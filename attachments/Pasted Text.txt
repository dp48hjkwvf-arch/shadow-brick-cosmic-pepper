LIFEOS — ASISTENTE PERSONAL INTEGRAL

Aplicación web progresiva (PWA) para iPhone, desarrollada desde GitHub

1. OBJETIVO DEL PROYECTO

Quiero desarrollar una aplicación personal llamada LifeOS, destinada a organizar mi vida académica, mis tareas, mis horarios, mis eventos, mis rutinas, mis hábitos y mi tiempo.

La aplicación debe funcionar como un asistente personal accesible desde mi iPhone, con una interfaz moderna, rápida, intuitiva y adaptada a dispositivos móviles.

El proyecto se desarrollará utilizando GitHub desde un iPhone. Por eso, necesito una estructura de código organizada, instrucciones claras y herramientas que permitan editar, publicar y mantener la aplicación sin depender de una computadora.

La aplicación debe construirse como una Progressive Web App (PWA) que pueda publicarse en una dirección HTTPS e instalarse desde Safari en la pantalla de inicio del iPhone.

No quiero una simple página web ni una maqueta visual. Quiero una aplicación funcional con almacenamiento persistente, navegación completa, calendario, tareas, rutinas, hábitos, notificaciones y estadísticas.

Objetivos principales

1. Organizar mis actividades escolares y personales.
2. Administrar horarios y calendarios.
3. Registrar tareas y fechas de entrega.
4. Recibir recordatorios y notificaciones.
5. Crear rutinas y alarmas compatibles con iOS.
6. Gestionar hábitos mediante checklists.
7. Planificar sesiones de estudio.
8. Priorizar actividades importantes.
9. Preparar el día siguiente.
10. Conservar mis datos de forma segura.
11. Poder instalar la aplicación en mi iPhone.
12. Poder actualizarla mediante GitHub sin tener que reinstalarla manualmente cada vez.

Prioridad absoluta: funcionalidad real, compatibilidad con iOS, almacenamiento persistente, facilidad de uso y una experiencia similar a la de una aplicación nativa.

2. TECNOLOGÍA Y ARQUITECTURA

Selecciona una arquitectura sencilla, estable y compatible con el desarrollo desde un iPhone.

2.1. Tecnologías propuestas

Utiliza preferentemente:

* HTML5.
* CSS3.
* JavaScript moderno o TypeScript.
* Una arquitectura de componentes ligera, como React con Vite, si la herramienta de desarrollo lo permite.
* Web App Manifest.
* Service Worker.
* Cache API.
* IndexedDB para almacenamiento local.
* Supabase u otro servicio compatible para autenticación, base de datos y sincronización cuando sea necesario.
* Web Push API para las notificaciones push.
* GitHub para almacenar y versionar el código.
* GitHub Pages para publicar la aplicación estática, si la arquitectura seleccionada es compatible.

Puedes proponer una arquitectura diferente si mejora significativamente la compatibilidad, pero debes explicar por qué.

No agregues dependencias innecesarias ni servicios de pago obligatorios sin explicar su función.

2.2. Separación entre frontend y backend

Diseña la aplicación de forma que la interfaz y los servicios de servidor estén claramente separados.

El frontend debe encargarse de:

* Mostrar las pantallas.
* Gestionar formularios.
* Presentar tareas y eventos.
* Mostrar el calendario.
* Administrar las interacciones.
* Guardar datos localmente cuando corresponda.
* Registrar las preferencias del usuario.
* Solicitar permisos de notificación mediante acciones explícitas.

El backend, cuando sea necesario, debe encargarse de:

* Gestionar cuentas.
* Sincronizar datos.
* Almacenar información en la nube.
* Procesar solicitudes de notificaciones push.
* Mantener las suscripciones de los dispositivos.
* Programar avisos que deban enviarse en el futuro.
* Validar las solicitudes.
* Proteger la información.

No intentes implementar operaciones de servidor utilizando únicamente JavaScript ejecutado en el navegador.

2.3. Restricciones de GitHub Pages

Si utilizas GitHub Pages:

* Publica el frontend mediante HTTPS.
* Configura correctamente las rutas y la ubicación base de la aplicación.
* Comprueba que los recursos funcionen bajo la dirección real del proyecto.
* Evita utilizar rutas absolutas que rompan la aplicación cuando se publique dentro de un subdirectorio.
* Incluye instrucciones de despliegue desde GitHub.
* Configura las actualizaciones para que no dejen a los usuarios atrapados en una versión antigua de la aplicación.

No supongas que GitHub Pages proporciona una base de datos, un servidor de notificaciones o funciones backend.

Si se necesitan esas funciones, intégralas con un proveedor externo apropiado.

3. COMPATIBILIDAD CON IPHONE Y SAFARI

La aplicación debe estar diseñada prioritariamente para iPhone.

3.1. Diseño móvil

Implementa:

* Interfaz adaptable a pantallas pequeñas.
* Botones cómodos para utilizar con los dedos.
* Navegación inferior.
* Formularios sencillos.
* Tipografía legible.
* Tarjetas organizadas.
* Modo claro y oscuro.
* Compatibilidad con la orientación vertical.
* Tratamiento adecuado de las áreas seguras de la pantalla.
* Respeto por los espacios del indicador de inicio y la barra de estado.
* Ausencia de desplazamientos horizontales innecesarios.

Utiliza las propiedades CSS correspondientes para las áreas seguras del dispositivo y evita que los botones queden ocultos detrás de los elementos del sistema.

3.2. Instalación como PWA

La aplicación debe poder instalarse desde Safari mediante la opción de compartir y añadir a la pantalla de inicio.

Cuando esté instalada, debe abrirse en modo aplicación, sin mostrar la interfaz habitual del navegador.

Incluye:

* Iconos apropiados.
* Nombre de la aplicación.
* Nombre corto.
* Color del tema.
* Color de fondo.
* Configuración de orientación cuando sea necesaria.
* Pantalla de carga apropiada.
* Diseño independiente del navegador.

No afirmes que está instalada si solamente se ha abierto desde Safari.

Incluye instrucciones visibles para instalarla cuando se detecte que el usuario está accediendo desde un navegador compatible.

La aplicación debe seguir siendo utilizable desde el navegador aunque no esté instalada, pero debe explicar las diferencias entre ambos modos cuando sean relevantes.

4. MANIFIESTO WEB Y SERVICE WORKER

Implementa los archivos necesarios para que LifeOS funcione como una PWA.

4.1. Archivo manifest.json

Crea un manifiesto válido que incluya, como mínimo:

* name.
* short_name.
* start_url.
* scope.
* display configurado en standalone.
* background_color.
* theme_color.
* icons con los tamaños apropiados.

Comprueba que las rutas del manifiesto y de los iconos funcionen correctamente en la dirección publicada.

Si la aplicación se aloja bajo una ruta de proyecto de GitHub Pages, configura correctamente el alcance de la PWA.

4.2. Service Worker

Implementa un Service Worker que permita:

* Almacenar en caché los recursos necesarios.
* Mejorar la velocidad de carga.
* Gestionar estrategias de actualización.
* Mostrar una experiencia de carga apropiada.
* Recibir eventos push cuando el navegador y el sistema operativo lo permitan.
* Procesar eventos de notificación.
* Abrir la sección adecuada al tocar una notificación.

Utiliza estrategias de caché que eviten mostrar información obsoleta cuando sea importante.

No almacenes información personal sensible en cachés públicas innecesarias.

Controla las actualizaciones para evitar problemas cuando se publique una nueva versión.

La aplicación debe informar cuando haya una actualización disponible y permitir aplicarla de manera segura.

5. NOTIFICACIONES PUSH EN IOS

Esta es una de las funciones más importantes de LifeOS.

Quiero recibir recordatorios en mi iPhone incluso cuando no tenga abierta la interfaz de la aplicación, siempre que el sistema operativo y la configuración lo permitan.

5.1. Requisitos de iOS

Implementa las notificaciones push web respetando los requisitos de Apple.

Considera los siguientes aspectos:

1. En iOS 16.4 o posterior, las notificaciones push web están disponibles para aplicaciones web añadidas a la pantalla de inicio.
2. El usuario debe instalar la aplicación desde Safari utilizando la opción de añadir a la pantalla de inicio para utilizar las notificaciones push web compatibles.
3. El manifiesto debe estar correctamente configurado para funcionar en modo aplicación.
4. El permiso de notificaciones debe solicitarse como consecuencia directa de una acción del usuario.
5. Debe existir un botón explícito llamado «Activar notificaciones».
6. El permiso no debe solicitarse automáticamente al abrir la aplicación.
7. Debe comprobarse si el navegador y el contexto actual admiten las funciones necesarias.

No supongas que la aplicación puede enviar notificaciones push si no está instalada, si no se han concedido los permisos o si el dispositivo no admite la función.

5.2. Flujo para activar las notificaciones

Implementa este flujo:

Paso 1: el usuario abre LifeOS.

Paso 2: si las notificaciones no están configuradas, la aplicación muestra una explicación breve.

Paso 3: el usuario pulsa «Activar notificaciones».

Paso 4: si todavía no ha instalado la PWA y el sistema requiere la instalación, muestra instrucciones para añadirla a la pantalla de inicio.

Paso 5: solicita el permiso del navegador únicamente como respuesta a la acción del usuario.

Paso 6: si el permiso es concedido, registra la suscripción push del dispositivo.

Paso 7: envía la suscripción al backend para poder enviar notificaciones en el futuro.

Paso 8: muestra una notificación de prueba cuando exista un servicio de envío configurado y el usuario lo solicite.

Si el permiso es rechazado, explica cómo habilitarlo en la configuración correspondiente, sin repetir solicitudes de manera insistente.

5.3. Backend para las notificaciones

No intentes enviar notificaciones push únicamente desde el frontend.

Implementa un backend o servicio compatible que pueda:

* Guardar las suscripciones push.
* Asociarlas al usuario o dispositivo correspondiente.
* Generar mensajes.
* Enviar las notificaciones.
* Procesar errores de entrega.
* Gestionar suscripciones caducadas.
* Eliminar suscripciones inválidas.
* Programar avisos futuros.

Puedes utilizar Supabase con funciones de servidor y un sistema de programación compatible, u otra arquitectura equivalente.

Si eliges otro proveedor, explica cómo se integra.

Las claves privadas y los secretos del servidor nunca deben incluirse en el código público de GitHub.

Las claves públicas que deban utilizarse en el frontend pueden exponerse cuando el protocolo correspondiente lo requiera, pero los secretos privados deben permanecer en el backend.

5.4. Recordatorios programados

Quiero configurar notificaciones para:

* Entregas de tareas.
* Exámenes.
* Eventos.
* Clases.
* Rutinas.
* Hábitos.
* Sesiones de estudio.
* Preparación del día siguiente.

Cada recordatorio debe incluir la fecha, la hora y el contenido que corresponde.

El backend debe programar las notificaciones que requieran ejecución en una fecha futura, cuando la arquitectura lo permita.

No dependas exclusivamente de temporizadores de JavaScript que solo funcionen mientras la página está abierta.

Si se utiliza un proveedor externo de notificaciones, configura las tareas programadas necesarias.

Si el proveedor elegido no permite programar notificaciones directamente, implementa una alternativa compatible o explica claramente qué servicio adicional se necesita.

5.5. Contenido de las notificaciones

Ejemplos:

* «LifeOS: mañana debes entregar el trabajo de Matemática».
* «LifeOS: tu examen de Historia es mañana».
* «LifeOS: es hora de comenzar tu rutina».
* «LifeOS: tenés una sesión de estudio programada».
* «LifeOS: revisá tus pendientes para mañana».

Las notificaciones deben ser claras y concisas.

Al tocar una notificación, la aplicación debe abrir la pantalla o el registro relacionado cuando sea técnicamente posible.

No muestres información privada innecesaria en la pantalla de bloqueo.

5.6. Reprogramación y cancelación

Si modifico la fecha de una tarea, sus recordatorios deben actualizarse.

Si elimino la tarea, deben cancelarse los avisos asociados que todavía estén pendientes.

Si completo una tarea, deben cancelarse sus recordatorios pendientes cuando corresponda.

Evita duplicados cuando se edite un registro o se vuelva a guardar una suscripción.

Registra los identificadores de los avisos programados para poder gestionarlos.

Si una notificación ya fue enviada, no intentes eliminarla como si todavía estuviera programada.

5.7. Limitaciones reales

Distingue entre:

* Notificaciones push enviadas por un servidor.
* Notificaciones locales programadas en el dispositivo.
* Avisos internos que aparecen solamente mientras la aplicación está abierta.

No afirmes que las tres modalidades son equivalentes.

La implementación debe documentar las capacidades de la plataforma seleccionada.

Las notificaciones push requieren conectividad para recibir nuevos mensajes desde el servidor. Los límites de entrega, los permisos, los modos de ahorro de energía y las condiciones del dispositivo pueden afectar su recepción.

No prometas que todas las alarmas funcionarán exactamente como las de una aplicación nativa.

Si una rutina necesita una alarma local con garantías que la PWA no puede ofrecer, informa de la limitación y ofrece una alternativa compatible.

6. ALMACENAMIENTO LOCAL Y SINCRONIZACIÓN

LifeOS debe conservar mis datos de manera fiable.

6.1. Almacenamiento local

Utiliza IndexedDB para almacenar los registros que necesiten persistir en el dispositivo.

Incluye:

* Tareas.
* Materias.
* Horarios.
* Eventos.
* Rutinas.
* Hábitos.
* Notas.
* Sesiones de estudio.
* Preferencias.
* Historial.
* Datos de configuración.

No dependas exclusivamente de variables de JavaScript ni de almacenamiento temporal.

6.2. Funcionamiento sin conexión

Permite consultar los datos almacenados localmente cuando no haya conexión a Internet.

Cuando sea posible, permite crear o modificar tareas y eventos sin conexión.

Si existe sincronización con un servidor, guarda temporalmente los cambios y sincronízalos cuando se recupere la conexión.

No pierdas los cambios locales si falla una solicitud al servidor.

Muestra claramente si hay cambios pendientes de sincronización.

Las funciones que dependan de un backend o de una conexión deben identificarse correctamente.

6.3. Sincronización opcional

Si implementas sincronización entre dispositivos, utiliza una base de datos en la nube.

Supabase es una opción posible, pero puedes elegir otro servicio compatible.

La sincronización debe contemplar:

* Identificación del usuario.
* Autenticación.
* Permisos de acceso.
* Conflictos entre cambios.
* Cambios realizados sin conexión.
* Eliminaciones.
* Recuperación ante errores.
* Separación de datos entre usuarios.

Si la aplicación se mantiene como una herramienta local de un solo dispositivo, no añadas una cuenta obligatoria sin una necesidad real.
